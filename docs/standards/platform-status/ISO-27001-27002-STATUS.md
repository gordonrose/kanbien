# ISO 27001 / 27002 Platform Status

Source gate: [`ISO-27001-27002-GATE.md`](/home/gordon/kanbien/docs/standards/ISO-27001-27002-GATE.md)

## Overall

- Current status: `Partial`
- Summary:
  The repo is getting stronger in documentation, traceability, and evidence
  discipline, which is a good fit for ISO-style controls. It is still weak in
  mature operational procedures, supplier/dependency governance, and broader
  access-governance controls.

## 1. Policy And Control Alignment

- `Pass` The change does not contradict existing security policy.
  Current repo docs are internally coherent.
- `Pass` Any required policy, standard, or runbook updates are identified.
  Change-artifact requirements and newer skills now help drive this.
- `Partial` Security exceptions are documented and approved.
  Direction exists, but formal exception handling is not yet strong.

## 2. Access Control

- `Partial` Access to the changed component follows least privilege.
  Good direction exists, but enduring permission architecture is incomplete.
- `Partial` Administrative or privileged access is restricted and reviewable.
  Root-user privileged access is now more explicitly restricted through
  `rootRoles`, but review/governance is not yet mature.
- `Pass` Shared credentials are avoided or explicitly controlled.
  No shared-credential anti-pattern is evident in current implemented work.

## 3. Asset And Information Handling

- `Partial` Information handled by the change is classified or at least understood.
  Understanding is improving through docs; formal classification is missing.
- `Partial` Sensitive information has handling rules.
  Some handling rules exist; no general policy mapping layer yet.
- `Partial` Retention, deletion, and audit implications are considered where relevant.
  Current entity lifecycle docs help, but no broader retention architecture yet.

## 4. Secure Operations

- `Partial` Operational procedures for the change are documented when needed.
  Some runbooks exist, but coverage is narrow.
- `Partial` Deployment, configuration, and maintenance responsibilities are clear.
  Code/config ownership is decent; deployment/ops governance is weak.
- `Fail` Logging, backup, restore, and support implications are understood.
  Logging is auth-centric only, and backup/restore/support architecture is not
  mature.

## 5. Supplier And Dependency Control

- `Partial` New vendors, hosted services, or material third-party dependencies are reviewed.
  Review discipline exists conceptually, and the initial `Resend` email
  provider path is now explicitly captured in the `notificationDelivery`
  artifact chain, but there is still not a strong governed supplier-control
  layer.
- `Partial` Security ownership of the dependency is understood.
  Sometimes true in practice, and the owner of the outbound email provider path
  is now clearer than before, but there is still not a mature documented
  supplier-security process.
- `Fail` Exit or replacement implications are considered for critical dependencies.
  No generalized dependency exit strategy is documented.

## 6. Change Management

- `Pass` The change is documented before implementation.
  Increasingly true through PRDs and artifact chain.
- `Pass` The change is reviewed and approved at the right level.
  Repo process encourages this clearly.
- `Pass` The change can be tested before production use.
  Strong test planning/process exists.
- `Partial` The production rollout is controlled.
  No mature release architecture yet.

## 7. Incident And Continuity Impact

- `Partial` Security incident implications are understood.
  Better in current auth areas than across the whole platform.
- `Fail` Business continuity or resilience implications are understood.
  No real continuity model yet.
- `Fail` The change does not create an unsupported single point of failure without approval.
  This is not yet governed strongly enough at the platform level.

## 8. Auditability

- `Pass` Records exist to show what changed, who approved it, and what was tested.
  The repo is getting strong here through its artifact chain.
- `Pass` The design and implementation decisions are traceable.
  PRDs, ADRs, API contracts, dictionary, and skills help a lot.
- `Partial` Control evidence can be produced later for audit or review.
  Better than before with root-role auditability and explicit authz mapping,
  but not yet broad enough for all future platform layers.

## Main Gaps To Close

- operational procedures and deployment governance
- backup/restore/support model
- supplier/dependency governance
- formal data classification and access review
