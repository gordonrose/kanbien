# Blog Accountability Workflow

## Purpose

Create a repeatable, low-friction way to turn repo progress and personal
lessons into publishable blog posts.

This workflow is meant to help chronicle the journey of building a SaaS
platform while keeping the writing:

- grounded in real repo work
- personal rather than generic
- reflective rather than performative
- consistent enough to sustain

## The Job

Use Codex as a weekly blog accountability partner.

Each session should:

1. infer the strongest story from recent repo work
2. ask the minimum set of focused questions needed to surface the lesson
3. identify the tension, opinion shift, or surprising discovery
4. turn the result into an outline or draft
5. keep the post anchored in the repo rather than drifting into generic startup
   or AI commentary

## Weekly Prompt

Use this prompt when you want to kick off the weekly session:

> Help me produce this week’s blog post from my SaaS platform journey. Start by
> identifying the strongest story from what changed in the repo and what I
> learned this week. Then ask me the minimum set of focused questions needed to
> turn it into a strong post. After I answer, turn it into an outline or draft
> grounded in the repo and my actual experience.

## Monthly Reflection Prompt

Use this prompt once per month:

> Help me write this month’s reflection on building this SaaS platform. Focus
> on what changed in my thinking, architecture, process, and use of
> AI-assisted development. Ask sharp questions, then turn my answers into a
> reflective post grounded in the repo’s actual evolution.

## Weekly Session Structure

### Step 1. Repo Scan

Start with:

- recent commits
- recently changed docs and features
- notable standards or process changes
- any meaningful shifts in design thinking

### Step 2. Story Selection

Choose one primary angle:

- build log
- design lesson
- process lesson
- founder reflection

### Step 3. Focused Interview

Ask only 5 to 8 questions.

Questions should aim to surface:

- what changed
- why it mattered
- what felt easy or hard
- what belief changed
- what tension or trade-off is worth sharing

### Step 4. Distillation

Turn the answers into:

- a one-sentence thesis
- 3 to 5 supporting points
- a suggested outline
- title and subtitle options

### Step 5. Optional Draft

If asked, turn the outline into a first draft that is:

- reflective
- specific
- technically grounded
- free from generic AI/startup cliches

## Writing Guardrails

- prefer concrete turning points over broad claims
- keep mistakes and course-corrections visible
- use the repo as evidence when useful
- do not flatten everything into “AI changed everything”
- preserve uncertainty where it is real
- optimize for credibility over hype

## Good Questions To Reuse

- What shipped that actually changed the shape of the platform?
- What did you think would be easy that turned out to need more structure?
- What is the real lesson here, beyond the code change itself?
- What belief do you hold now that you did not hold a week ago?
- If someone copied this move too early or too late, what would go wrong?

## Suggested Output Formats

- `outline only`
- `short draft`
- `full draft`
- `idea bank update`
- `monthly reflection`
