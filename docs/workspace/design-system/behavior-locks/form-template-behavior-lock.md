# Form Template Behavior Lock

## Purpose

Lock the behavioral rules for the `Form Template` family before picker, drawer,
and control seams are promoted out of the current
`/design-system/templates/form` implementation.

This artifact governs the parent page pattern first.
Child seams extracted from it should inherit these rules rather than redefining
the form-page contract ad hoc.

## Review Status Legend

- `approved`:
  behavior should be preserved in the reference pack and downstream child
  extractions
- `rejected`:
  current behavior should not be treated as the target
- `undecided`:
  behavior still needs iteration before being locked

## Scope

- Family:
  `form-template`
- Review outcome:
  parent behavior lock under refinement
- Current source surface:
  `/design-system/templates/form`
- Related reference pack:
  `docs/workspace/design-system/reference-packs/form-template-reference-pack.md`

  `docs/workspace/design-system/templates/form-template.md`
- First child extraction:
  `Simple Select` child seam now started through dedicated child artifacts;
  `Drawer Select` remains a larger separate follow-up seam
- Active next child extraction:
  `Time Picker` child seam now started through dedicated child artifacts under
  `docs/workspace/design-system/behavior-locks/time-picker-behavior-lock.md`

| `FT-012` | Single-date pickers must close immediately after a day is chosen, while multi-step date ranges must keep the panel open long enough to complete the range intentionally. | Distinguishes quick single-value selection from staged range authoring. | `initializeFormDatePickers()` closes `single` mode on day selection, but `range` and `range-time` keep the panel open and advance through staged selection. | `approved` | Single-date can be fast; ranges need a more deliberate flow. |
| `FT-013` | Range and range-with-time pickers must use explicit staged guidance: choose a start date first, then an end date, and enable `Done` only when the range is complete. | Captures the nuance we learned around multi-step scheduling instead of treating it like a generic calendar. | The current range summary text changes with `selectionStage`, and the `Done` button remains disabled until an end date exists. | `approved` | The staged guidance is important and shouldn’t be left implicit. |
| `FT-014` | If a range end date is chosen earlier than the start date, the picker must normalize the order rather than leaving an invalid backwards range. | Keeps range behavior forgiving without creating broken state. | The current date-picker logic swaps the start and end when the second selection falls before the current start value. | `approved` | The control should recover gracefully from reverse selection. |

| `FT-022` | Choice controls must preserve two distinct grouping patterns: conventional radio/checkbox groups and a shared-statement checklist where one explanatory statement governs multiple checkbox rows. | Records a nuance the older lock missed and keeps group semantics from drifting back to one default pattern. | The current `Checkboxes with shared statement` group uses a lead statement above the option stack instead of repeating that language inside every row. | `approved` | The shared-statement checkbox pattern matters for dense admin copy. |

## Exit Criteria For This Step

This behavior lock step is complete when the parent template rules above are
stable enough to guide:

- the reference pack
- the parent template note
- the first child extraction discussion

Do not treat future child seams as governed if they contradict these approved
page-level rules without an explicit follow-up review.
