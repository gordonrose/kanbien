## Direction Captured In This Draft

- Tenant administration is root-only in the first draft.
- The governing operator boundary is `RootUserAdmin`.
- The current tenant lifecycle rows should be treated as:
  - capability boundary: `root`
  - tenant context rule:
    root-operated tenant lifecycle capability; no tenant-member session or
    tenant-selected actor context in v1
- The first draft covers the full tenant entity lifecycle surface you asked for:
  - create
  - exact view
  - list
  - update
  - explicit deleted exact view
  - explicit deleted list
  - soft delete
  - reactivate
  - full delete
- Tenant identity is modeled with:
  - `tenantId` UUID generated by the system
  - `bizId` as a mandatory durable business identifier
  - `name` as a mandatory tenant display/business name
  - `createdByRootAdminUserId` as a system-managed durable reference to the
    root admin user UUID that created the tenant
  - `category` as a business-rule-ready tenant classification with initial
    values:
    - `customer`
    - `demo`
    - `test`
  - `status` as a business-rule-ready tenant lifecycle/status field with
    initial values:
    - `draft`
    - `live`
    - `disabled`
    - `inactive`
  - standard system-managed lifecycle and audit fields

## Pressure-Test Decisions Applied

- `bizId` is treated as a durable first-class tenant fact, not a derived or
  mutable related lookup.
- `bizId` uniqueness is assumed to apply on a normalized active value.
- `bizId` is treated as immutable after creation.
- `name` is mandatory but not unique. It remains business/display metadata
  rather than the tenant's canonical stable identifier.
- `createdByRootAdminUserId` is a durable system-managed tenant attribute and
  must be set from the authenticated root session, not from client input.
  It should bind to the durable `rootUserId`, not to a transient session ID or
  auth-principal-only identifier.
- `category` and `status` are modeled as explicit durable tenant fields so
  future business rules can bind to them without relying on inferred state.
- `category` is mutable only by privileged root operators and is intended for
  administrative correction rather than routine business workflow.
- Create defaults tenant `status` to `draft`.
- In v1, any status can transition to any other status under RootUserAdmin
  control; human policy governs the choice rather than hard system transition
  rules.
- `disabled` and `inactive` are intentionally distinct:
  - `disabled` is for commercially or policy-constrained tenants where login
    visibility may remain but some actions are blocked
  - `inactive` is for tenants whose logins are blocked altogether
- Normal reads, lists, and updates exclude soft-deleted tenants by default.
- Soft-deleted tenants are visible only through explicit deleted-read and
  deleted-list capabilities.
- Reactivation is modeled as an explicit capability instead of overloading
  generic update semantics.
- When `deletedAt` is populated, tenant `status` is forced to `inactive`.
- Reactivation restores the tenant to its pre-delete status rather than leaving
  it permanently `inactive`.
- `createdByRootAdminUserId` should be exposed on exact tenant reads.
- `createdByRootAdminUserId` does not need to appear on list responses in the
  first slice.
- `updatedByRootAdminUserId` and `deletedByRootAdminUserId` are out of scope
  for the first slice.
- `reactivateTenant` should restore the pre-delete status automatically rather
  than accepting a caller-supplied replacement status.
- `removeTenant` should require explicit confirmation and a reason even in v1.
- `category` and `status` should be filterable in tenant list routes in v1.
- Soft delete and full delete are intentionally separate capabilities.
- Full delete is allowed in v1 because no tenant-bound durable entities exist
  yet, but later tenant-owned data will require explicit purge/retention rules.

## Deliberate Scope Choices

- This draft is focused on tenant entity-adjacent CRUD/lifecycle capabilities
  only.
- Initial create remains tenant-record-only.
- Initial create should still stamp creator identity durably on the tenant via
  `createdByRootAdminUserId`.
- It does not yet define:
  - tenant admin bootstrap
  - tenant user bootstrap
  - tenant membership assignment
  - tenant-scoped authorization roles
  - tenant self-service signup
- No frontend route is assumed yet, even though the future root-admin shell may
  expose these capabilities later.

## Main Questions To Review Before Implementation

- Whether status changes should remain part of `updateTenant` in the first
  slice or be split into an explicit status/lifecycle transition capability for
  clearer policy and audit separation.
- How the system should persist the pre-delete status so `reactivateTenant`
  can restore it deterministically:
  - dedicated `preDeleteStatus` storage on the tenant
  - audit/log-driven restoration is not recommended because status restoration
    is a durable domain behavior, not just an audit concern
- What exact action restrictions will later hang off `disabled` versus `inactive`
  once tenant-bound user and domain capabilities exist.

## Full Delete Tradeoff

`removeTenant` is still the highest-risk part of this draft, but your current
scope decision is reasonable because tenants do not yet own other durable
domain records.

Why it still matters:

- tenant records are likely to become owners of other durable domain data soon
- once related records exist, permanent removal can break auditability,
  billing/reporting history, referential integrity, and historical correctness
- the repo's architecture guidance says not to remove durable entity-linked
  data casually and to prefer explicit compatibility/purge strategies

What that means in practice:

- `softDeleteTenant` is still the safe default administrative lifecycle action
- `removeTenant` can exist in v1 for the narrow tenant-only world we have now
- once tenant-bound durable data is introduced, removal should become guarded
  by explicit purge/retention policy rather than remaining casually available

My recommendation:

- implement `removeTenant` in v1 while the tenant is still an isolated durable
  record
- keep `softDeleteTenant` and `reactivateTenant` as the normal reversible
  administrative lifecycle path
- treat this as a temporary safe window: once tenant-owned entities arrive, add
  explicit purge/retention rules and tighten `removeTenant` accordingly
